## 问题与修复

启动时，前端原逻辑优先从浏览器 `grapher_config` 缓存选模型，并在它与后端配置不一致时静默调用 `save_config`。旧浏览器状态可能覆盖后端已保存且可用的模型；实跑开始时界面显示的旧模型与后端原配置不一致，增加了选错 provider 的风险。

已修改 `src/App.tsx`：初始渲染不采用缓存模型；启动配置以 `bootstrap.config` 为准，只把所得配置更新到浏览器缓存，不再在加载阶段回写后端。验证时先把后端恢复为原配置 `zicc/gpt-6-sol`，刷新保有测试模型缓存的前端；设置界面显示 `zicc/gpt-6-sol`，后端配置文件也保持该值。此次没有修改 Planner prompt 或工具描述。

### 发现与归因

1. **API 边界缺陷，归于实现模型；验收覆盖有缺口。** `server/users.ts` 的 cursor 仅含 `{version,offset}`，没有关联原查询。在注入 25 条 Alpha 和 25 条 Beta 的数据源时，把 `q=Alpha` 首屏返回的 cursor 用于 `q=Beta`，接口返回 200 且只给出 `b20` 至 `b24`，静默跳过前 20 条 Beta。正常 UI 在改查询时重置 cursor，因此此缺陷不会由当前 UI 的常规操作触发。服务端模型选择了偏移 cursor，测试模型只覆盖畸形 cursor；Planner 的节点约束列出畸形、非规范、负数及越界 cursor，但没有规定跨查询复用的语义。原始目标和 JSON 合同也未明确这一点。最小修复是把规范化查询绑定进 cursor，并对不匹配的查询返回 400；在固定验收用例中加入跨查询复用。现有图编译与发布仅验证图结构和 Git 合并，不执行这类语义断言，因此未拦下它；这属于系统验收能力的缺口，不是系统合并造成的数据损坏。
2. **运行包装缺口，归于样例环境与任务边界。** 发布仓库的 `package.json` 只有 `node --test`，没有服务器入口、浏览器页面或构建脚本；目标又要求 package manifest 不变。模型按图节点要求交付了可调用的 handler 与可挂载的 UI 模块，而非可直接启动的网站。真实浏览器验收需要临时适配器和临时编译。此项不表示模块功能失败，但“13 项测试通过”不能单独证明发布产物可直接部署。优先给评测样例提供固定的运行适配器及真实浏览器验收工具，而不是给通用提示词添加项目专属实现步骤。

上述追加验收未修改原始发布仓库，保留 `cb7abba` 作为模型输出的可复核基线。
