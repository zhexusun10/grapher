# 三平台原生环境控制方案：随工作区交接，版本化运行状态

> 状态：中文方案讨论稿，尚未实现或验收；不是当前架构能力说明。文中的模式、对象、接口和配置均为拟新增能力。
>
> **硬约束：仅采用 Linux、macOS、Windows 原生执行。不采用 VM、WSL2、Hyper-V 隔离容器或依赖虚拟机的桌面容器后端，也不将它们保留为未来可选路线。Linux 本机 namespace 是宿主内核提供的原生进程/挂载隔离，不是虚拟机。**
>
> 本方案不修改 Planner、NodeAgent 或其他节点的提示词，不追加环境迁移说明，也不要求 Agent 做额外的环境绑定、搬迁或修复。Agent 继续完成原有业务任务；环境准备本来属于业务任务时，安装依赖仍是正常工作。
>
> “不改提示词”不等于“零运行配置”：用户需要选择执行模式、默认入口、管理范围及资源要求。任意宿主环境不能因此自动导入，任意 `activate/export` 也不会自动成为跨节点设置。

## 一句话结论

**环境和启动配置绑定当前 workspace 执行视图，随既有工作区所有权一起交接；历史快照只保存执行证据，不把节点重新绑回旧环境。三平台原生执行，共用状态模型，不另建一套与 workspace 冲突的节点环境分配机制。**

A → B → C 的线性链继续使用同一个活动 workspace。用户随后与 A 交互时，A 在最终 workspace 及其当前环境中继续自己的会话，不恢复 A 当年的代码或环境。Linux 原生 namespace 只扩展跨独立视图的路径隔离，不能改变这条基本合同。

平台适配集中在启动绑定、快照/克隆、路径和设备检查；Windows 原生依赖、CUDA、macOS MPS 均留在本机执行。原生能力不足时明确限制或拒绝，不换执行 OS，也不强制把既有工作区分配改成全图单槽。

## 1. 目标、当前缺口与保证范围

当前已经能继承项目内的 ignored 文件，包括依赖、环境、数据和权重；线性链和反馈也能独占传递完成目录。缺口在于：继承文件不等于下游进程使用了正确环境，文件组合也不能证明依赖兼容。

本方案的目标是：

1. 上游在已配置的默认环境中准备依赖后，下游无需因切换节点而重新安装。
2. 在提供相应能力的后端，共享不可变底层文件，减少大型 ML 环境的重复复制。
3. 活动 workspace 允许后续所有者正常修改环境，但不能覆盖已封存历史；并行分支使用既有独立工作区及隔离写入状态。
4. 线性继承和共享终端 follow-up 保留当前路径；跨物理槽的透明路径保证按后端能力单独准入。
5. 每次执行记录实际使用的代码、环境、启动配置和资源引用；普通继续使用当前视图，显式历史编辑才按既有合同回退输入。
6. Runtime 不识别所有包管理器，而是管理声明范围内的文件状态及明确的启动入口。
7. 三平台均有原生落地路线；不换执行 OS，不以另一平台的运行结果替代本机验证。

保证限定在同一兼容执行域及其声明范围内。不保证跨 OS、CPU 架构或 ABI 直接复用二进制，不自动合并不兼容环境，不修复业务代码错误，也不承诺恶意多租户隔离或自动识别业务程序写出的秘密。

环境版本不是与 Git head 一一绑定的：同一 E1 可以服务多个代码版本。当前绑定单位是 workspace 的当前执行视图；执行记录再固定实际使用的复合引用。物理目录、当前结果别名与历史执行记录必须分开。

## 2. 三平台的原生执行模式

### 2.1 不改变 workspace 的分配与继续语义

| 模式 | 工作区与调度 | 环境管理 | 保证边界 |
| --- | --- | --- | --- |
| 原生目录兼容模式 | 保留当前线性传递、并行分支、多父组合和共享终端 follow-up | 保留当前 Git 与 ignored 文件合同 | 旧 Run 的已有能力，不追加新保证 |
| 原生 workspace 绑定模式（三平台基线） | 使用既有工作区分配；同目录一个写入者，线性及共享终端继续直接接手当前视图 | 为视图增加 E/L、当前结果引用和独立环境快照；不按节点反复恢复旧版本 | 同一物理路径上的环境连续性；跨槽透明迁移、完整系统快照及权限隔离另行准入 |
| Linux 原生 namespace 扩展 | 在既有工作区之上提供固定逻辑路径，不改变节点会话或所有权交接 | 可靠快照及私有写层；具备能力时共享底层 | 可扩大并行分支、重建等跨物理槽场景的路径保证；内核、驱动及外部服务不进入快照 |

**单写者是 workspace 的所有权规则，不是让整个 Run 额外串行的理由。** 线性链本来按依赖交接同一目录；fan-out 仍由现有分配器创建独立视图，fan-in 仍组合代码/资源，普通 follow-up 仍按唯一终端 workspace 规则定位。

没有原生路径隔离时，Windows/macOS 不承诺任意不透明环境在不同槽中仍透明保持全部绝对路径。不能为补齐这个限制而自动把图压成一个固定槽、重写启动器或恢复节点历史。强能力要求不足时明确阻塞；兼容模式保留已有行为。

旧 Run 保留原生目录兼容模式。新增环境管理须显式初始化范围及默认入口，不在执行中悄悄改变 workspace、并发或发布合同。

### 2.2 各平台的原生落地路线

| 平台 | 工作区与启动 | 快照/存储路线 | 设备与限制 |
| --- | --- | --- | --- |
| Linux | 沿用既有目录交接和 bubblewrap 边界；可扩展 namespace 固定逻辑路径 | 内容快照/独立副本；验证后启用 reflink、分层文件系统或文件系统快照 | 本机 CUDA/ROCm 分别验证；namespace 本身不是环境快照 |
| Windows | 沿用实际 workspace 路径和所有权；stock Node/Pi/Git Bash 绑定该视图的 L；Job Object 管理生命周期 | 内容快照；只有实际文件系统支持时才用块克隆优化 | 保留 Windows Python/wheel、MSVC、CUDA；不新增文件权限隔离，不保证任意环境跨槽可迁移 |
| macOS | 沿用实际 workspace 路径和所有权；保留 Seatbelt 与进程组；按当前视图启动 | 内容快照；APFS 克隆经验证后优化 | 保留 macOS Python、Apple 工具链及 MPS；克隆不能消除跨槽绝对路径差异 |

Runtime/model/store、工作区分配和环境选择共用；三个原生适配器处理本机启动、快照和设备能力。文件克隆只优化历史保存、分支物化或重建，不代表每次节点交接都要克隆工作区，也不提供路径隔离。

### 2.3 选择规则

- 新 Run 明确本机平台/架构、环境范围、默认入口和资源要求；环境功能不重新决定哪个节点拥有哪个 workspace。
- 三平台优先验证现有线性链、共享终端 follow-up 和反馈的就地绑定；Linux namespace 扩展单独准入。
- 跨槽创建独立视图或恢复缺失目录时，检查环境布局兼容性。无法满足强路径合同则拒绝，不声称普通复制等价。
- 多父环境选择与可用工作区准备协调，但不能覆盖活跃写入者、擅自合并环境或用旧节点结果替换当前共享终端视图。
- 需要完整系统软件快照或额外隔离时，本机能力不足则阻塞；不换 OS，也不引入已排除路线。
- 不解析任务文本猜测后端，不自动把 CUDA/MPS 任务改成 CPU，不静默改变模式。

## 3. 统一状态模型与默认入口

| 概念 | 内容与作用 |
| --- | --- |
| 执行域 D | 本机平台/架构、原生工具链基线及可选受控根目录快照、路径布局、管理范围、后端合同及兼容条件 |
| 域实例 | 本机执行上下文与布局；不是强制把一个 Run 分配为一个新固定目录 |
| 环境版本 E | 不可变的环境快照及父引用；不是节点永久专属环境，也不是禁止修改活动目录 |
| 启动配置 L | 默认入口、Shell/hook 和变量模板的不可变记录；当前绑定随工作区视图交接 |
| 当前工作区 W | 既有 workspace 的当前代码/资源、E/L 绑定、最近完成引用、活跃代际及 lineage |
| 执行视图 V | W 的当前状态在本次执行中的视图；线性继续可直接复用，不必新建副本 |
| 写租约 | 当前执行对 W 及其环境范围的独占写权，随既有所有权交接 |
| 执行输入/结果 | 实际使用和产生的 D、代码、E/L、资源引用；历史记录不随 W 后续变化改写 |

```text
执行输入 I = (domain, codeRef, environmentRef, launchRef, resourceRefs)
完成结果 O = (domain, codeRef', environmentRef', launchRef', resourceRefs')
```

**先按现有 workspace 合同确定 W，再记录和绑定该视图的 E/L；I 是实际输入的记录，不是每次启动都必须恢复的一套旧目录。** 节点、会话、当前视图和历史执行分别标识，不能只按节点名、旧 cwd 或 Git head 选择环境。

同一 W 的当前状态可以从 E1 推进到 E2；E1 的历史快照仍不可变。完成事件同步推进 W 和其 lineage 中被表示节点的当前复合结果别名，保持代码、资源、E/L 一致；各次执行的 before/after 引用保持原值。多父选择则检查各输入结果的 `(E, L)`。

### 3.1 初始化与导入

- 首次执行前固定基础状态、默认解释器/工具入口和路径，按配置预建默认环境，或导入与该域及布局兼容的原生环境。
- 基线记录具体解释器、ABI、工具链及必要外部库条件；Linux 使用受控根目录基线时，另记录其文件快照 digest，不只记录版本标签。
- 已有环境依赖的路径必须保留；不满足时，由用户明确选择初始化构建或拒绝导入，不进行包管理器专用路径修补。
- 环境版本只在兼容平台/架构和布局内复用；Windows venv、macOS 二进制和 Linux 二进制不互换。显式跨域重建产生新版本，不伪称复用了 E1。
- 环境初始化不需要新增维护 Agent。可使用预制原生基线、明确配置的构建命令，或由最上游业务节点在默认环境中正常安装依赖。

最上游节点可以从 E0 准备出 E1，但不是全图共享可写环境的管理员。独立根节点从所选基线独立执行，不会自动收到另一根节点的修改。

### 3.2 文件继承不等于默认入口切换

**安装到默认环境的修改自动继承；新建其他环境不会自动成为默认入口。**

例如 A 在项目范围新建 `other-env`，并在某次 Bash 中激活它，其文件可以被记录，但 B 的普通 `python` 不因此改用它。普通 `export`、`source`、`conda activate` 仍遵守标准进程作用域。

L 的修改只来自用户显式配置，或预先声明的项目启动配置/构建策略；修改形成新版本并按分支继承，不成为所有运行节点的可变全局设置。Runtime 不解析任意 Shell 文本、扫描环境名称或读取任务文本来猜测激活意图，也不要求 Agent 增加环境绑定动作。

默认未配置更新策略时 L 保持不变。配置 Conda 等带激活 hook 的入口时，后端必须通过已声明入口建立工具进程使用的环境，不能仅设置一个目录或只在某次 Bash 子进程里激活。

### 3.3 启动环境的来源

- 业务启动变量来自当前 W 的 L 及本次资源绑定，不直接继承宿主全部环境变量，也不重放所选节点旧执行的启动配置。
- 外层 `PATH`、`VIRTUAL_ENV`、`CONDA_PREFIX`、`PYTHONHOME`、`PYTHONPATH`、动态库路径和 Shell 启动变量等，不得未经配置泄漏到新执行；必要的宿主值按显式策略导入。
- 凭据和设备选择按授权/租约注入，具体绑定记录在执行中，不把秘密或设备临时身份封入 E/L。
- 引擎使用可信的固定入口，不能因业务 PATH 修改而换成另一份 Node/Pi。
- 验证对象是工具实际启动出的进程，包括 Pi 对 PATH 的二次处理，不只是 Rust 启动参数。

### 3.4 输入来源优先级：当前视图与历史分开

| 操作 | 工作区/环境输入 |
| --- | --- |
| 普通线性依赖交接 | 接手已完成父工作区当前视图；绑定其当前 E/L，不恢复该父节点更早执行 |
| 对唯一共享终端树中的 A 普通 follow-up | 使用最终共享 workspace 当前代码、资源、E/L；A 只继续自己的对话 |
| 活跃执行 steering | 继续已有视图和租约，不重建或切换环境 |
| 接受合法反馈 | 使用请求固定的发送方完成视图及 E/L，遵守已有排空、校验和移交规则 |
| fan-out、独立续跑或缺失目录重建 | 按已有分配规则从所需复合结果物化独立视图；不能覆盖另一活跃 workspace |
| 普通失败重试 | 保留原失败视图的部分工作；原始 I 仍保留为证据 |
| 显式 Graph 历史消息编辑 | 按已有合同恢复对应执行的输入 I，执行相应失效规则 |

没有唯一共享终端 workspace 的续跑仍遵守已有独立分支规则，不任意挑一个“最新目录”。共享终端目录被清理后，普通 follow-up 重建的是当前终端结果，而不是 A 当年的结果；不能恢复其环境布局或引用时明确失败。

## 4. 路径与工具执行边界

### 4.1 Linux 原生 namespace：独立视图，相同逻辑路径

以下是逻辑布局示例，不是强制目录名：

```text
节点内部看到：
  /workspace          当前项目
  /opt/environment    默认环境
  /home/agent         受管理的 HOME
  /run/grapher        本次 Runtime 控制数据

本机实际保存：
  .../slot-1          A 或后续独占接手者的视图
  .../slot-2          B 的独立视图
  .../slot-3          C 的独立视图
```

A、B、C 看到的 `/opt/environment` 相同，可以映射到不同版本和写层。A 生成的启动器指向 `/opt/environment/bin/python`，B 仍在同一路径执行它，无需修改内容。

项目采用 `/workspace/.venv` 等位置时，可声明该子路径为环境范围，并从代码及普通 ignored 组合范围中排除。不能同时赋予它两种管理语义。

### 4.2 三平台原生就地交接：同一个 workspace，不按节点恢复

```text
同一物理目录 W（可含已声明的 .venv 等环境范围）：
  A0 在 W 工作：E0 -> E1
       交出 W 的写权
  B0 在 W 工作：E1 -> E2
       交出 W 的写权
  C0 在 W 工作：E2 -> E3
       交出 W 的写权
  用户继续与 A 交互：A1 在同一个 W、当前 E3 中继续
```

- 同一 W 和其环境范围保持单写者；不同工作区是否并行仍由现有调度和资源能力决定。
- 普通接手先校验当前视图，再转交写权和启动绑定；不 checkout 旧代码，不把 `.venv` 恢复为旧节点版本，不复制整套环境。
- 封存历史与允许后继修改活动目录不矛盾：历史字节保存于独立快照，活动 W 继续向前推进。
- 只有分支物化、历史编辑、缺失目录重建等既有操作需要准备/恢复内容；恢复使用可靠副本，不使用可写硬链接。
- 环境在 W 内或外部声明范围中均可，但必须随该 W 的视图和写权绑定，不能变成节点固有目录或多个活跃 W 的共享可写全局环境。
- 换实际路径时单独检查兼容性；不能用无条件复制承诺原生启动器和 editable 引用有效。
- HOME/USERPROFILE、PATH 等不隔离原生注册表、用户配置 API 或全局服务。

新功能是在已有交接上增加环境状态记录与启动绑定，不新增一个与现有 allocator 竞争的“固定槽分配器”。

### 4.3 所有相关工具使用同一视图

Pi、Bash、`read/write/edit`、搜索工具和本地扩展必须访问本次执行的同一视图。不能只为 Bash 设置环境，而文件工具、扩展或用户 Shell 仍访问另一份代码。

本地扩展/MCP 子进程须绑定本次视图和启动配置；外部服务和远程工具不属于文件环境快照，使用者必须明确接受其边界。Linux namespace 执行不提供绕过该视图的工具通道；普通原生 workspace 执行仍受本机权限和可信工具限制，不因此获得新的隔离保证。

源路径、物理存储路径、节点 cwd 和会话存储路径分别记录。快照在正确的本机视图中采集，不能按视图外的路径语义解析符号链接。预热/复用进程必须校验域、L、环境输入及视图租约，不能只因模型或旧 cwd 相同就复用。

稳定路径只覆盖声明的域内布局。旧程序硬编码的任意宿主路径、动态构造的源项目地址，不自动改写；现有工具路径适配也不能被当作内核级映射。

## 5. 例子一：A 准备一次，B/C/D 使用同一环境

下述强路径并行例子使用 Linux 原生 namespace 扩展。其他平台保留已有 fan-out 分配规则，但跨槽环境继承必须符合声明的兼容条件；不满足时阻塞强保证，不自动把分支塞进同一目录串行重放。

```text
A：准备 ML 环境 ─┬─→ B：数据统计（CPU）─┐
                └─→ C：训练模型（GPU）─┴─→ D：汇总并验证结果
```

B/C 独立使用同一输入数据，C 不需要等待 B 的报告。训练依赖预处理结果时，应保留真实业务依赖，不能为了并行省略边。

A 在默认环境中安装锁定依赖，完成后封存为 E1，启动配置仍为 L0。示例不代表已验证任意 NumPy/Pandas/PyTorch 组合。

| 节点 | 进入时环境 | 做什么 | 完成时环境 |
| --- | --- | --- | --- |
| A | E0 | 安装业务依赖 | E1 |
| B | E1 | 生成数据报告 | E1 |
| C | E1 | 训练并生成 checkpoint | E1 |
| D | E1 | 使用 B/C 的文件结果 | E1 |

```text
共享、不可变的 E1
  ├─ B 的私有写层：没有环境持久修改
  ├─ C 的私有写层：没有环境持久修改
  └─ D 的私有写层：没有环境持久修改
```

- B/C/D 不需要重新安装；无持久变更时仍引用 E1，不强制生成新版本。
- 代码、产物及已声明缓存不写入环境版本。
- 并发需要独立 workspace 和实际资源租约；同一活动目录不能分配给两个写入者。
- 就地交接无需恢复环境；额外分支物化或重建可能复制文件，“无需重装”不代表这些场景没有复制成本。

只读 E1 只能在任务确实不需要环境写入、且后端能落实只读约束时使用。默认提供可写视图，不要求 Agent 临时申请解锁。

## 6. 例子二：B 升级依赖，不能改变 C 的输入

假设 E1 中 NumPy 是 1.26，B/C 都选择 `(E1, L0)`：

```text
                         B：升级 NumPy
                        /   E1 + B 的修改 -> E2（NumPy 2.x）
A 完成：E1（NumPy 1.26）
                        \   C：继续用 E1（NumPy 1.26）
```

B 执行正常的 `pip install`，Runtime 保证默认入口绑定当前视图，写入不修改 E1。B 完成后，普通下游 F 继承 `(E2, L0)`。

这里 B/C 是 fan-out 的独立分支，不是 A → B → C 的线性继承。Linux namespace 中 C 可以正在训练，仍读取 E1；原生分支视图只有兼容布局时才能提供对应保证。若暂时串行调度，C 也只能从自己的分支输入开始，不能因 B 先结束就拿到 E2，更不能为准备 C 而回退 B 的活动 workspace。

未改变的底层内容在支持共享的后端继续共享；新文件、替换、删除和必要元数据由版本表达，不能通过修改 E1 得到 E2。

## 7. 例子三：B/C 都改环境，D 不能盲目拼接

```text
                  B：升级依赖 -> E2
                 /                 \
A：E1                                 D：整合两路结果
                 \                 /
                  C：安装依赖 -> E3
```

即使 E2/E3 修改的文件没有重叠，也不证明依赖兼容。代码和业务文件可按现有或已声明资源规则组合；环境与启动配置必须单独选择。

| 输入情况 | 默认处理 |
| --- | --- |
| B/C 都使用 `(E1, L0)` | D 使用 `(E1, L0)` |
| 一路为 E1，另一路为后代 E2，L 相同 | 只有策略明确允许时选择 E2，否则报告歧义 |
| 独立 E2/E3，或不同 L | 不自动合并；阻塞，或执行明确的权威输入选择策略 |
| 已配置统一构建规格及入口 | 根据已选代码/锁文件构建新的 E4/L4，不拼接目录 |

多父准备不能以最后执行的节点、最新时间戳或某个空闲目录的内容作为默认权威输入。这里是在选择新的组合输入，不是对唯一共享终端 workspace 的普通继续；后者直接使用该当前视图，不重新从祖先环境中选择。

选择 E2 不代表 C 的产物在 E2 下业务兼容。产物保留来源结果引用；业务验证仍由 D 的原有任务完成。选择来自配置或用户，不通过新增提示词让 D 猜测、搬迁或修复环境。

## 8. 例子四：一个 workspace 向前推进，A 也继续最终视图

```text
只有一个活动 workspace W：
  A0 完成 -> B0 接手 -> C0 接手 -> 用户向 A 发 follow-up -> A1 接手
     E1        E2        E3                            从 E3 开始
```

假设 B/C 确实改了环境；没有修改时仍可沿用同一 E。所有节点的 cwd 不因节点身份改变，只有写入者和执行代际变化。

### 当前状态与历史记录

| 对象 | C0 完成后的含义 |
| --- | --- |
| W 的当前完成结果 | C0 结束时的代码、资源、E3/L_current |
| 被 W lineage 表示的 A/B/C 当前结果别名 | 与该当前复合结果一致，不能只有 Git head 前进而 E/L 留在旧版本 |
| A0 的历史执行结果 | 仍记录当时的 E1 及对应代码/资源，不能被 C0 改写 |
| B0/C0 的历史执行结果 | 分别保留当时的输入/结果引用，不因后来 follow-up 改写 |

### 用户继续与 A 交互

1. 现有 Runtime 定位表示 A 的唯一终端 workspace W。
2. A1 接手 W 当前写权；使用 C0 留下的当前代码、资源和 E3/L_current，**不恢复 E1，也不重建一份 A 专属工作区**。
3. A1 继续 A 自己的会话，不导入 B/C 的对话，不添加环境说明。
4. A1 未改环境时继续 E3；改了则在当前 E3 基础上形成 E4，W 向前推进。
5. 完成事件一致推进 W 及所表示节点的当前复合结果别名；沿用已有共享终端 follow-up 特例，保留 B/C 完成状态，不单因环境改变另加一轮下游重跑。

环境版本谱系描述状态变化，workspace lineage 描述当前树表示哪些节点，二者不是同一个概念，但完成时必须协同推进当前引用。只有显式历史编辑才恢复相应执行输入并触发既有失效规则。

**不可变的是历史快照，不是活动 W；会话属于节点，当前环境属于 W。**

## 9. 例子五：审查 B 反馈给 A

```text
A0：完成实现，使用 E1/L0
  ├─ B0：审查/复现，完成结果可能使用 E2/L0
  └─ C0：验证（Linux namespace 模式下可能仍在执行）

B0 --反馈--> A1：接手 B0 的完成执行视图
                         |
                         v
                     C1：验证修复结果
```

1. 固定 B0 的复合结果和反馈正文，并记录被审查的 A0 结果。
2. 检查反馈合法性、预算、来源与目标代际。
3. 等待受影响写入者结束；不强制暂停进程。待处理反馈保留发送方完成 workspace 及 E/L，不先让无关写入者覆盖它。
4. 校验并移交 B0 的完成视图写权；A1 获得新代际，B0 封存快照保持不可变。
5. A1 继续 A 的历史，不导入 B 的对话；逻辑或固定实际路径保持不变。
6. A1 未改环境/入口时沿用 E2/L0；修改后，C1 继承新完成引用。

反馈视图必须按其固定结果交接，不用新基线偷偷替换。兼容当前反馈要求，缺失或被外部修改的交接视图阻塞，不自行选另一份“最新环境”。

A1 收到的消息仍只有来源标签和实际反馈正文，末尾控制标记移除，没有环境指导。接受、预算耗尽和过期反馈不触发移交。B 后续执行不能回退或覆盖 A1 的当前视图。

## 10. Runtime 负责什么，Agent 不需要做什么

| 事项 | Runtime | Agent |
| --- | --- | --- |
| 选择模式、域与默认入口 | 按配置准入并固定引用 | 不推断环境迁移策略 |
| 继承上游环境 | 随既有 W 所有权移交当前 E/L；必要物化才使用快照 | 不因换节点重装依赖 |
| 路径稳定 | 保留既有 cwd；跨槽保证按原生能力准入 | 使用原有命令及项目路径 |
| 进程环境 | 应用 L、入口 hook 和资源绑定，清除旧实例绑定 | 不额外激活/重绑定 |
| 业务依赖修改 | 隔离或串行管理，记录并封存 | 业务需要时正常安装 |
| 多父歧义 | 执行显式策略或阻塞 | 不通过新增提示词猜测 |
| 失败、反馈、恢复 | 管理引用、快照、租约和会话 | 不手动搬运执行状态 |

不新增环境维护 Agent，不改变反馈协议、会话归属、现有 workspace 分配及共享终端继续合同，不重写历史对话。环境管理不能另行决定 A 应回到哪个旧节点目录。

## 11. 文件范围与环境状态闭包

| 范围 | 处理方式 |
| --- | --- |
| 固定基础状态 | 原生工具链或受控根目录文件基线引用及兼容检查 |
| 环境持久状态 | 不透明快照，包含必要文件元数据；每执行选择一个权威输入 |
| 项目代码 | Git 版本与多父组合，不包含已声明的环境/独立资源范围 |
| 数据、权重、checkpoint | 独立资源版本及节点写入视图，记录来源结果 |
| 明确可重建缓存 | 独立缓存策略，不参与环境版本选择 |
| 临时目录、进程文件、Runtime 控制数据 | 执行级范围，不假装为可继承环境；需要保留的业务文件须声明持久范围 |
| 凭据 | 按授权注入，不进入 E/L/资源快照 |
| 未声明状态 | 受管理范围内的未知持久写入保守记录；不自动当缓存丢弃，不宣称范围外状态已被快照 |

### 11.1 Linux 原生 namespace 的文件闭包

不能只快照 `/opt/environment`，再宣称可以继承任意系统软件。`/usr`、`/usr/local`、`/etc`、包管理器数据库、动态库缓存及 HOME 下的工具链/配置，必须归入固定文件基线或持久快照。

Linux 要支持系统软件安装，须另行提供并验证受控根目录、私有写层及所需权限，在本机内核上运行，不修改宿主全局系统。只隔离项目环境的 namespace 不具备这项能力；当前把宿主 `/` 作为底座的方式也不构成该保证。未声明外部状态应不可见或按显式只读输入暴露，不能留下不可追踪的可写出口。

这是 Linux 原生能力的可选扩展，不是三平台环境继承的共同前提。Windows/macOS 工作区绑定不承诺全系统文件闭包，也不通过改变执行 OS 实现它。

快照合同要明确符号链接、权限、硬链接、所有者、xattr/文件能力等必要元数据，以及删除/替换语义。后端无法保存环境所需元数据时拒绝，不拿普通字节复制冒充等价系统快照。

### 11.2 原生 workspace 绑定只管理声明范围

原生基线以兼容条件约束，不能快照或隔离任意系统库、注册表、宿主驱动和服务。基线变化时重新校验，不能继续声称旧 E 可完整恢复。

Windows 原生进程仍可能以用户权限写到声明范围外；设置环境变量、单写者调度和 Job Object 都不能阻止它。本模式不提供此类写入隔离；要求完整闭包或额外写入防护时，若本机原生后端不能提供则拒绝，不把受信任约定当成隔离。macOS/Linux 原生适配也不得为兼容而放宽既有源项目/兄弟工作区访问边界。

可信执行下，Runtime 对声明范围实施独立快照、恢复和校验，未知全局副作用不被伪装为版本化环境。

### 11.3 范围划分与资源

环境位于项目子目录时，初始化检查重叠、挂载冲突及已跟踪文件冲突。范围转移显式记录，不靠“像 `.venv`”的启发式判断，也不暗改源项目 `.gitignore`。

环境范围必须从 host Git 快照和普通 ignored 文件组合中排除，进入单独版本通道；这需要改造 `workspace/files` 边界，不能只新增启动参数。仍受旧合同管理的其他 ignored 文件继续继承。

数据同样共享不可变输入、私有化修改。只读挂载必须真实可执行且明确声明；正常保存 checkpoint 的输出位置保持可写。资源文件组合不保证业务兼容，环境兼容也不证明产物可加载。

## 12. GPU、缓存和凭据

### 12.1 GPU 是外部能力，不随环境文件搬迁

| 本机平台 | 设备验证要求 |
| --- | --- |
| Linux | 在实际 workspace 或 namespace 中分别验证 CUDA/ROCm 等声明能力、驱动接口及计算 |
| Windows | 在真实 Windows Python/框架与 Job Object 生命周期边界中验证原生 CUDA 等能力 |
| macOS | 在本机 macOS Python/框架及既有访问边界中验证 MPS；没有相应硬件/能力时不宣称支持 |

不因框架 import 成功就认为设备可用；不借用另一平台设备检查的结果。

- 资源需求来自 Run/项目的显式策略或节点资源映射，不通过解析任务文本或追加提示获取。
- 对 GPU 执行真实的小型张量运算并同步完成；不只解析 `nvidia-smi` 或设备枚举。
- 租约覆盖所有受同一 Runtime 管理、使用同一物理设备的域/Run；单个 Run 的 `maxParallel` 不是设备调度。
- 初期每个可独立分配设备默认独占。MPS/统一内存等无已验证硬隔离能力的平台采用保守串行策略。
- `CUDA_VISIBLE_DEVICES` 是选择而非显存隔离；MIG 等也只在实际平台验证后声明。
- CPU、内存、磁盘配额另行声明能力；不能因控制 GPU 数量就宣称资源不可能耗尽。其他宿主程序仍可占用设备，租约不等于整机硬隔离。
- 不自动升级宿主驱动、不改 batch size、不在 CUDA/MPS 不可用时悄悄换 CPU。

本方案不快照或替换本机内核、驱动与活动 GPU 状态。保存的是进程结束边界的文件状态和启动描述，不是暂停训练后跨节点续跑的进程状态。

### 12.2 避免缓存制造环境分叉

普通运行也可能写 `__pycache__`、编译缓存和配置文件；“未安装依赖”不等于“没有环境文件变化”。

- 可明确重定位的运行缓存由 L 指定独立范围，例如 Python 字节码缓存；不要求 Agent 每次手动设置。
- 对环境持久范围比较内容和合同要求的元数据，无变化时沿用 E；不能只因写层非空就生成新版本。
- 未声明写入保守记录。不能为了避免 E2/E3 歧义而任意删除包目录、`.cache` 或新配置。
- 下载缓存只有确认锁、原子落盘和并发行为安全后共享，否则隔离。
- 编译缓存按 OS/架构、ABI、工具链、源码和设备架构等条件区分，不跨平台或不同基线盲用。
- 共享底层不代表零 I/O：快照扫描、哈希、copy-up 大文件和 checkpoint 更新仍需预算。原生恢复尤其要测量完整复制成本。

### 12.3 凭据

按授权提供本次执行所需凭据，注入位置不作为环境或资源输入继承。原生 Windows 权限仍可能允许读取其他宿主凭据，不能因此宣称保密隔离。快照排除注入位置，但不承诺自动识别或脱敏任意业务文件中的秘密。引擎、凭据和业务环境不能互相覆盖管理范围。

## 13. 共用原生后端接口与能力准入

拟新增执行后端接口，由 Linux、macOS、Windows 原生适配器实现；版本选择、调度、反馈和存储事件仍只有一套：

| 操作 | 合同 |
| --- | --- |
| 准备域、报告能力 | 校验本机平台、基线、布局、存储、工具入口及可用设备 |
| 接手/准备视图 | 先按 workspace 合同定位当前视图，再绑定 E/L；只在需物化时恢复复合引用 |
| 启动执行 | 复用对应本机 launcher，在该视图内启动可信引擎，记录身份并流式输出 |
| 排空与封存 | 确认受管理写入者结束，保存不可变状态及校验信息 |
| 移交/释放 | 完成事务后转交新代际或释放资源；旧代际不能再获调度/交接权 |
| 恢复/回收 | 校验引用、遗留进程和租约，按保留策略处理 |

Runtime/model/store 保持权威，复用现有原生启动、进程组/Job Object、Git 与文件快照代码。平台差异集中在 namespace 挂载、原生路径校验、文件克隆/元数据和设备检查，不新增另一套业务运行系统。

环境快照与必要物化逻辑可共用；APFS、Windows 文件系统和 Linux 优化分别探测。所有权代际仍归既有 workspace 管理，令牌不代替进程排空或访问控制。不能给代码和环境各分配一个互相矛盾的写入者。

Linux namespace 中的代码/Git 输入须有正确的视图内引用；Git alternates 只暴露必要只读对象数据库，不能为省复制放开可写源项目、兄弟工作区或全局 HOME。三平台现有访问边界不因环境继承而放宽。

能力至少分别报告：

- 固定实际布局或 namespace 布局，以及是否支持同时存在多个固定路径视图；
- 声明范围的快照、元数据、私有写入和真实只读约束；
- 文件克隆/共享底层存储，以及 Linux 可选受控根目录能力；
- 进程排空、取消、重启租约校验；
- 本机 ABI、设备和资源限制。

能力按实际组合准入，不能按 OS 名称直接认为成立。可靠副本可用于必要的快照物化，但不代表任意原生环境可换路径；只读属性、junction、APFS 克隆或逻辑约定不能冒充进程级路径/权限隔离。

三平台就地交接、共享终端继续和 Linux 独立并行视图分别测试；缺失本机能力、快照或设备时明确失败，不静默换模式或换执行平台。

## 14. 封存、失败、恢复与发布

### 14.1 从第一版版本控制就具备最小事务

执行开始前固定 I、实际入口和租约代际；完成时：

1. 模型返回完成后等待受管理进程/写入者结束。超时或无法确认时失败并保留视图，不交给下游。
2. 采集一致的代码、环境和资源状态；原子文件系统快照不能替代“业务安装/写入已经完成”的检查。
3. 持久化快照及校验信息，形成 O。E/L 改变即使 Git head 不变也算结果变化，但失效处理仍遵守既有共享终端 follow-up 特例，不能因此擅自重跑完成后继。
4. 在同一业务事务中推进 W 的当前复合引用、被表示节点的当前别名，并提交历史完成引用及反馈请求；不得引用未成功持久化的状态。
5. 提交成功后才允许下游、反馈或槽的新代际写入。

快照与 SQLite 不是一个文件系统事务：先持久化快照，再提交引用；事务失败产生的无引用快照可后续回收，但不能留下已完成节点引用缺失状态。崩溃恢复需要识别准备中视图、未提交快照和已提交结果，不能把“目录存在”当作完成证据。

### 14.2 失败和重启

- 普通失败重试保留原失败 workspace 的部分工作和原始 I；普通成功后 follow-up 使用当前共享终端结果，两者都不等于恢复旧输入。
- 显式 Graph 历史编辑才恢复选定执行的 I，并按既有规则处理失效；不能回退另一活跃 writer 的目录。
- 必须释放/重用失败 workspace 时，先保留失败视图。保存失败或仍有写入者则阻塞，不能覆盖部分工作。
- 重启不自动续跑旧进程；先校验本机进程树、槽/namespace 租约及代际，不能仅清除 PID 记录就接管仍有写入者的路径。
- 已提交反馈继续按固定 O 排空和校验。未提交完成不能产生半份交接。
- 缺失环境、资源、启动配置、固定路径或后端时明确失败。
- 本机基线、驱动、平台/架构或路径布局变更要重新准入；不偷偷以新基线解释旧版本。

### 14.3 发布复合结果，不随意搬环境目录

- 代码和业务资源按已声明的源项目交付合同发布。
- 同时持久化可启动结果描述，包含 D、代码、E、L、资源及能力要求。仅有 E 引用不足以启动 editable 项目。
- 用户可通过 Runtime 在兼容域中启动该结果；不自动激活宿主源目录环境，也不保证宿主裸 `python` 可运行。
- 已声明的环境子目录不随意搬回不同路径的源项目；新模式按当前终端 workspace 的复合结果引用交付。源项目已有环境不因此自动删除、覆盖或激活；保留它不代表它与已发布结果同步。
- 当前 ignored 发布会交付源项目内 `.venv` 等文件；选择新模式并把它声明为环境范围后，这部分改为环境引用交付。必须在配置/批准时明确显示，不能暗改旧 Run 合同。
- Planner/Serial 继续源项目原生写入。扩展其后端须另立合同；它们的全局安装或源环境修改不会自动替换已固定的环境版本。后续批准的源代码变更与环境更新分别按策略接收。

回收考虑当前终端视图、运行、反馈、发布、失败视图及历史引用。原生结果可能依赖 workspace 的绝对布局；清理后继续 A 时，恢复当前终端代码/资源及 E/L 的同一复合结果，不能用 A 的旧快照替代。缺失所需状态或布局时明确失败。保留策略不默认永久归档所有大环境和 checkpoint。

## 15. 与当前实现的关系及落地顺序

保留已有线性传递、fan-out 独立视图、fan-in 文件组合、反馈协议、会话独立性和 ignored 快照能力。新增环境通道不把这些描述为尚未实现，也不把本提案描述为现有保证。

实现边界主要是 Runtime/model/store、native/sandbox 原生适配、workspace/files 范围划分、engine 启动和会话路径记录。UI 增加模式、保证范围、缺项、资源要求和发布描述展示；不需要三套业务 Runtime 或修改节点提示词。

### 阶段一：三平台现有 workspace 的环境绑定

- 为现有 W 增加当前 E/L、复合结果引用及必要环境范围；明确历史记录、节点当前别名与活动视图的区别。
- 三平台复用现有原生 launcher、allocator 和写所有权；优先验证 A → B → C 就地交接及用户继续 A 的最终视图，不新增固定槽调度器。
- 绑定实际工具进程入口，清理旧实例启动变量；所有文件/Bash 工具和本地扩展使用同一 W。
- 保留旧 Run 和兼容模式；范围、启动配置及发布合同须显式初始化。
- Linux 固定逻辑路径扩展独立设计，不作为其他平台原生绑定的前提。

### 阶段二：版本继承与最小可靠性闭环

- 实现环境与启动配置的独立选择、快照、写代际，以及资源/代码的范围排除。
- 接入既有线性传递、fan-out/fan-in、反馈、共享终端 follow-up 和清理后重建；跨槽兼容性不足时明确阻塞强保证，不重写工作区流程。
- 同步实现 before/after 历史引用、W 当前引用与 lineage 当前别名的事务推进、崩溃失败关闭和原失败状态保留。
- 实现最小可启动发布描述及其引用保留；禁止静默改变环境文件发布合同。
- 三平台分别通过真实解释器、启动器、editable 和进程生命周期测试后，才开放对应模式。

### 阶段三：原生 ML、快照优化和扩展恢复

- 分别验证本机 Linux CUDA/ROCm、Windows CUDA 及 macOS MPS；没有实际设备证据的组合继续标为不支持/未验收。
- 接入跨 Run 设备租约、缓存重定位及安全共享、CPU/内存/磁盘能力。
- 完善历史编辑、长期保留、引用回收、原生启动/取消异常恢复与快照损坏处理。
- 验证 APFS 克隆、实际支持的 Windows 块克隆及 Linux reflink/分层快照；不支持时采用可靠副本并公开成本。
- 测量大型环境/权重/checkpoint 的扫描、复制和 copy-up 成本；就地交接不得无故全量恢复，独立分支物化与 Linux 并行视图另给预算。
- 新增并行能力必须是本机原生能力且有真实证据，不能以路径重写或全局链接冒充透明映射，也不能绕过本方案的硬约束。

## 16. 验收标准

以下均为待验证项目，不是已通过结论。测试按本机平台/架构、模式、文件系统和设备分别记录；Linux 结果不能替代 Windows/macOS 原生证据，CPU 或 fixture 结果不能替代 GPU/真实进程验证。

### 通用状态与入口

- [ ] A 在默认环境安装一次后，B/C 无需重新安装即可使用。
- [ ] 普通 `python/pip` 及配置的 Conda 入口使用当前视图，没有外层实例或宿主环境绑定泄漏。
- [ ] Console script 与 editable 引用保持声明路径，读取当前节点代码，而不是源项目或另一分支。
- [ ] 新建其他环境及一次性 `activate/export` 不会静默修改下游默认入口；显式 L 更新按分支隔离。
- [ ] 环境/启动配置变化而 Git head 不变时，当前引用、反馈与下游选择仍正确；共享终端 follow-up 不被错误失效规则破坏。
- [ ] 多父独立 E/L 不被静默合并；权威选择记录清晰。
- [ ] 普通运行的已声明缓存不制造环境分叉；未声明持久写入不被随意丢弃。

### 三平台模式

- [ ] Linux、Windows、macOS 均使用本机真实引擎、工具链和解释器；不依赖已排除的执行路线。
- [ ] 三平台 A → B → C 始终交接同一个活动 workspace，环境从当前状态继续，不按节点恢复或额外复制。
- [ ] C 完成后用户继续 A，A 使用最终 W 的代码、资源和 E/L，保留 C 的产物且只继续 A 的会话。
- [ ] A follow-up 改环境后，当前 W 及被表示节点的当前复合别名一致推进，B/C 保持完成，历史 A0/B0/C0 引用不变。
- [ ] fan-out 的 C 从自己的输入视图运行，不错误继承独立 B 的环境修改；其准备不回退 B 的 workspace。
- [ ] Linux 原生 namespace 并行视图中 B 升级依赖，正在运行的 C 仍使用旧版本，且没有修改宿主全局系统或其他视图。
- [ ] 当前并行、所有权移交及旧 Run 语义保留；不为环境功能新增全图单槽串行或节点专属工作区。
- [ ] Windows/macOS 无并行路径隔离或完整系统快照时不冒充支持；严格能力要求失败，而不是改用另一 OS。
- [ ] 跨 OS/架构/布局的导入明确拒绝或显式重建；不存在隐式二进制迁移。
- [ ] 本机快照、基线或设备能力不可用时失败，不静默换模式。

### 生命周期、发布与资源

- [ ] 线性槽复用不覆盖历史；反馈接收方只继续自己的会话，没有新增环境指导。
- [ ] 受管理后台写入者、未释放句柄和原生遗留进程阻塞不安全封存/交接。
- [ ] 注入“快照成功后事务失败”“提交后崩溃”“原生进程启动/取消失败”等故障，完成/反馈引用与租约保持一致。
- [ ] 失败重试保留部分工作；显式历史编辑恢复指定 I；普通 follow-up 和清理后续跑使用当前终端复合结果，缺失状态明确失败。
- [ ] 新模式发布后，用户通过结果描述在兼容域启动正确代码、环境及资源；旧 Run 的文件交付行为不变。
- [ ] CUDA/ROCm/MPS 在实际后端中分别执行计算并同步；设备并发不超出已验证租约能力。
- [ ] 快照保存环境所需元数据；大型文件、三平台原生恢复和 Linux 并行共享性能有实测预算。
- [ ] 固定执行配置和原有任务时，全流程无需环境维护 Agent、迁移提示词或额外绑定步骤。
