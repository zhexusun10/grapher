# Architecture: boundaries and contracts

> **Audience:** Developers changing Grapher. For product capabilities and setup, use the [README](../../README.md); for operation and safety, use the [user guide](../user-guide.md).
> **Scope:** Component ownership, graph compilation and contract navigation.
> **Maintained with:** [compiler.rs](../../backend/src/compiler.rs), [core tests](../../backend/tests/core.rs) and the owning modules below.

## Component boundaries

```text
Goal -> Partitioner --serial--> Pi agent in source
             |
             '--graph--> Planner -> Graph IR -> Compiler -> Approval
                                                             |
                                                        Rust runtime
                                                             |
                                                   Pi task executions
                                                             |
                                                     Git publication
```

| Component | Owns | Does not own |
| --- | --- | --- |
| Partitioner | Tool-free route classification | Planning or execution recovery |
| Planner | Candidate task/edge mutations and explicit revisions | Dependency scheduling or completion authority |
| Compiler | Graph validation and topology | Model calls or workspace allocation |
| Runtime | Dispatch, execution transitions, feedback and recovery | Coding decisions inside a task |
| Workspace layer | Git snapshots, physical slots, composition and refs | Agent conversations or access permissions |
| Native environment layer | Admission, managed evidence and launch bindings | A second project-file version channel |
| Pi | Model calls, tools and provider authentication | Run state transitions |
| React UI | Backend projections and user commands | Persisted execution truth |

Ordinary scheduling has no persistent LLM coordinator. Planner turns are explicit lifecycle operations, not scheduler ticks. Prompts beside the implementation are production inputs: [Planner](../../backend/resources/prompts/planner.md), [Partitioner](../../backend/resources/prompts/partitioner.md).

## Graph compilation

```ts
interface Graph {
  originalGoal: string;
  nodes: Array<{ id: string; task: string }>;
  edges: Array<{ from: string; to: string; feedback: boolean }>;
}
```

Graph IR, persisted events/checkpoints, APIs, Planner tools and the editor all use `nodes[].id` as the stable node identifier; edges reference it through `from` and `to`. Node objects contain only `id` and `task`. Edges contain only `from`, `to` and `feedback`, and are unique by ordered `(from, to)` pair. Retired `name` node fields and `relation` edge fields are rejected, not aliased or migrated. Old graph/session formats and retired Planner tools are unsupported; there is no history translation.

Filesystem/ref components preserve portable node IDs; other IDs use a bounded
slug and content hash. Windows device stems are escaped before the dotted hash
is added (`CON.<hash>` is still reserved). This mapping never changes Graph IDs
or rewrites recorded execution paths or commit identities.

### Optional feedback capability

Settings **Enable Feedback** (`feedbackEnabled`) defaults to `false`, including when absent from older settings. Each subsequent Planner launch binds `GRAPHER_FEEDBACK_ENABLED` from its configuration, including prepared-process launches. When off, `edit_graph` edge items accept only `from`, `to` and optional `delete`: its schema and description contain no feedback protocol. Pi's schema validation rejects the omitted field rather than silently enabling it. Model-facing tool outputs (`edit_graph` results and `read_graph` projections, including overflow snapshots) omit the `feedback` field, retained feedback routes and feedback-specific warnings/notes, without altering the saved candidate on disk. Rejected edits preserve their diagnostic codes and validation failure, but `E207`/`E208` are described as retained graph constraints without injecting the unavailable protocol. The Planner must preserve required paths in the final batch graph. Atomic rewiring may replace those paths without exposing invalid intermediate graphs; if no valid final graph can preserve the constraints, request a user graph repair. Constraints are never silently discarded. When on, the optional `feedback` field and its protocol description return; `maxFeedback` remains an independent budget.

The frontend always renders the session's actual graph, including existing feedback edges, ports, hints and reviewer/budget indicators after Settings is switched off. The entire edge-type legend is omitted for sessions with feedback disabled and no retained routes; historical routes remain visible even when an older config lacks the setting. A saved legacy config without the field defaults off rather than inheriting today's global toggle. Only uncommitted planning without a saved config falls back to the current default for its legend.

All graph commit entrypoints (new Graph JSON, draft edits, Planner revisions and manual node additions) reject **new or retargeted** feedback routes when disabled, including requests carrying stale enabled configs. Existing routes may be retained or removed within that same Run; they are not authorization to add routes to another Run. Settings are published by same-directory atomic replacement. Only an absent settings file uses the caller's initial configuration; unreadable or malformed settings fail explicitly instead of restoring an old opt-in. This is a capability for subsequent planning/edits, not cancellation of already committed work: Graph IR, transcripts, queued verdicts and existing execution/replay semantics remain intact. Custom prompts and user-authored history are not rewritten.

Coverage: [Planner tool/schema checks](../../scripts/check-pi-extension.ts), [prepared binding](../../scripts/prepared-host.test.mjs), [graph projection](../../scripts/graph-elements.test.ts), [settings persistence](../../scripts/bootstrap-settings-ui.test.mjs) [graph ingress/concurrent settings](../../backend/src/feedback_settings_tests.rs) and [manual node validation](../../backend/src/manual_node_tests.rs).

### Validation and tool projections

Compiler validation requires:

- Nonempty, unique node IDs and nonempty tasks; valid edge endpoints; no self-edges or duplicate edges.
- Ordinary edges form a DAG. Independent roots need no artificial connecting edges; new mutations reject redundant dependency edges.
- Each feedback source has at most one target, which must be an ordinary dependency ancestor of that source.

The compiler returns `executionBatches`, `rootNodes`, `terminals` and warnings. Batches describe topology, not scheduler-wide barriers; dispatch readiness belongs to [Runtime](runtime.md#scheduling-and-concurrency). Plans accept only `rootNodes`, not the retired `roots` spelling. Replay and new mutations use the same compiler validation, including redundant-dependency rejection.

`read_graph({})` reads the current planning candidate as formatted JSON using `edit_graph`'s active node and edge vocabulary, not the runtime's approved execution graph. It reloads the file bound at Planner launch and shares Pi's native file-mutation queue with `edit_graph`, so it observes earlier successful edits and excludes rejected edits. Workspace switching does not change the binding; continuation and subsequent planning attempts bind their own candidate. Reading does not compile, repair, or mutate the candidate, and missing/malformed data fails explicitly rather than becoming an empty graph. Both inline output and overflow snapshots contain only `nodes` and `edges`, with nodes represented as `{id, task}` and edge `from`/`to` values referencing those ids (including `feedback` only when Feedback is enabled; when disabled, `read_graph` omits the `feedback` field and any retained feedback routes while leaving the saved candidate unchanged). The stored `originalGoal` is omitted from tool output, not erased from the candidate. Task text is unchanged. The normal tool declaration makes inspection discoverable; `promptSnippet` is omitted and no extra reading workflow is injected into bundled or custom system prompts.

Like Pi's native tools, `read_graph` bounds model-visible output using the SDK's `truncateHead` (2000 lines or 50KB). Its description states only the reading contract, without preannouncing truncation limits or overflow files. A truncated result identifies a complete per-read `planner-graph-snapshot-<uuid>.json` beside the candidate, outside project snapshots, accessible through ordinary `read`/Bash. Like mutation overflow, it uses Pi-style `[Showing lines 1-<shown> of <total>. Full output: <path>]` in `content` (adding the byte limit when it is hit), plus Pi's `details.truncation` and `details.fullOutputPath` fields. That file is a point-in-time output, never an authoritative write input or a live mirror; subsequent reads reload the candidate. This also handles a task string longer than the output limit without inventing another paging/query protocol. Ordinary small reads create no output file and do not duplicate the graph in `details`.

Planner mutations use `edit_graph({nodes?, edges?})`, with at least one edit across the two optional arrays. Node items are `{id, task?, delete?}`; edge items are `{from, to, feedback?, delete?}` (`feedback` is exposed only when enabled). Like Pi's `edit` on one file, a call describes multiple changes to one graph. Each node id and ordered edge pair may appear only once; duplicate targets are rejected rather than interpreted as sequential commands. Deletion targets are checked against the saved graph, explicit edge deletions apply before node edits and their incident-edge cascades, and edge upserts apply after node edits. An explicit edge deletion overlapping a node's cascade is accepted. Edges may reference nodes created in the same call. Only the final graph is compiled, once: invalid intermediate topology is allowed, but any error rejects the entire batch. Compilation runs asynchronously with cancellation, a ten-second timeout and a 1 MiB combined output cap; the queue remains held until the child closes. Compiler replies must contain an object plan or structured diagnostics, and warning lists must have the expected message shapes; malformed reply structure fails closed rather than authorizing a write. Successful candidates are published by same-directory atomic replacement; failed staging or replacement leaves the previous file intact, including for external preview readers. The tool declares `executionMode: "sequential"` and retains Pi's native candidate-path mutation queue for direct SDK calls. Separate calls commit independently in invocation order; failure does not roll back earlier successful calls or block later calls. Argument preparation tolerates stringified arrays and singleton collection items; Pi owns field types, nullable optional fields and unknown-property validation. Only `edit_graph` batches are supported; the retired `node` and `edge` implementations and node `name` aliases are removed.

Like Pi's native `write`/`edit`/`bash`, `edit_graph` returns concise plain-text feedback in `content`, not JSON state snapshots. Its schema describes inputs; its description preserves dependency direction and feedback continuation semantics alongside replacement, deletion and validation effects. The bundled Planner prompt owns dependency-workspace inheritance and merging, so the tool declaration does not repeat that explanation; custom Planner prompts supply their own business context. Pi-style tool mechanics supplement, rather than replace, these domain semantics. Concrete repair procedures belong in compiler diagnostics rather than tool declarations. `promptSnippet` is omitted so `edit_graph` is not inserted into the generated `<tools>` section, while `promptGuidelines` participates in Pi's normal generated prompt. As with native Pi tools, custom prompts use the tool declarations without extra prompt injection; neither the bundled Planner prompt nor user-supplied replacements receive a second set of tool-operation rules. Successful results summarize the node/edge edit counts, or report `created`, `updated`, `deleted` or an unchanged edge for a one-item batch, and include necessary side effects, such as edges removed with a deleted node, and actionable warnings. Rejections, including deleting a node or edge that does not exist, are returned with the result's own `isError: true` (no `tool_result` hook); they explain the failure and clarify that this call did not change the graph while earlier successful edits remain. Argument-shape errors use Pi's own validator messages. Missing-endpoint errors can identify an earlier failed batch containing that node in the same assistant turn, including a call rejected by Pi's argument validator. Pi's `tool_execution_start`/`tool_execution_end` events supply identities. Start events precede validation, so attribution projects only unambiguous primitive id/deletion intent with Pi-compatible coercion and never retains task text; successful batches clear matching node failures and `turn_start` clears the turn-local history. Unrelated failures are not blamed, and independent edits continue. For small results, `details` carries structured effects for logs and UI (`diagnostics`, `diagnosticCodes`, `relatedFailures`, `warnings`, `notes`); there is no `applied` flag. Overflow results instead carry `truncation`, `fullOutputPath`, and distinct diagnostic codes where applicable, without duplicating the unbounded message lists in `details`. Neither `content` nor `details` returns the complete graph, topology, roots or compiler plan. Acyclic `edit_graph` mutations automatically remove redundant direct ordinary dependencies implied by indirect paths and report the surviving paths as informational `notes` on a successful result rather than rejecting with `E209`. The compiler itself still rejects redundant direct edges with `E209` (including structured `dependencyPath` evidence) for direct Graph IR validation and replay. Because transitive reduction on a DAG preserves exact reachability, retained feedback routes keep their required dependency paths through the reduced graph, even with Feedback creation disabled. Cycles and all other blocking errors still reject the entire batch without pruning or saving.

The runtime reads the validated candidate file to publish durable preview/review graph events; that UI state does not have to pass through model-visible tool output. Pi result hooks may finish out of order even though graph writes are serialized, so the live UI buffers graph effects in tool-start order; failed calls drain without changing the preview, while transcript cards still update on completion. That buffer is scoped to the foreground stream and resets at each assistant turn. Raw-event previews mirror Pi's accepted primitive conversions, including case-insensitive boolean strings, `"0"`/`"1"` flags and required null string fields becoming the literal `"null"`; this does not replace Pi's input validation. Node deletion removes incident edges in the preview reducer, and edge updates apply the same acyclic redundant-edge pruning so the live preview stays aligned with the saved candidate. The preview and trajectory analysis support only current `edit_graph` calls and `isError`/`details` results; no retired tool or JSON-result projection remains. Tool output text is never interpreted as a compiler plan: business JSON from Bash or file tools cannot override topology or execution batches. An `edit_graph` call waits up to three seconds for the runtime's committed-graph snapshot when a Planner run is active and fails (graph unchanged) instead of validating without it. The saved candidate Graph IR is available through `read_graph`; the compiler plan remains internal to validation and runtime consumers. A root starts from the recorded source, not automatically from the Planner's private workspace; inheritance and snapshot timing belong to [Workspaces and Git](workspace-snapshots-and-feedback.md). Once a Run has published, delivered nodes cannot be removed. Tools receive the unremovable node IDs and reject removal with `E210`; the Planner must rework the node or add follow-up work. Execution requires final validation and approval.

Planner mutation output uses Pi's `truncateHead` limits (2000 lines or 50KB). Small results create no report file. The `edit_graph` description does not preannounce output limits; only an actually truncated result displays the overflow notice. Overflow results link a complete per-call `planner-edit_graph-result-<uuid>.txt` beside the candidate, outside project snapshots, readable through ordinary `read`/Bash. Filenames identify the tool and content purpose, without embedding node ids, task text or success/error state. All overflow tools share Pi-style head-range notices (`Showing lines 1-<shown> of <total>`, with the byte limit when applicable) and `Full output: <path>`, plus `details.truncation`/`details.fullOutputPath`, rather than separate report/snapshot protocols. An oversized first line gets `Line 1 is <size>, exceeds <limit> limit` instead of an invalid empty line range. The range describes the original output file, not the added status header or notice. Follow-up inspection uses ordinary `read`/Bash; the notice does not invent offset parameters for graph tools. These are immutable output snapshots, never graph write inputs. Success/rejection status stays visible even if a single node id or diagnostic line exceeds the byte limit. Truncated successful results also protect a bounded cumulative rerun-risk summary ahead of the body: `revisionImpact.rerunCount` comes from the compiler's Runtime invalidation calculation, not parsed warning prose or a second TypeScript algorithm. W304 requires a positive safe-integer structured count; missing or malformed impact evidence rejects the batch instead of guessing from prose or hiding the risk. A restored zero-risk draft has no stale risk header. The protected header also distinguishes updated tasks from original-task reruns on the latest workspace after dependencies complete; grouped node lists remain truncatable and available in the complete output file. Long local-effect and advisory lists are formatted one item per line; cascade counts and cumulative rerun warnings precede long detail lists. Report preparation happens before candidate publication: a report-write failure rejects the edit without changing the graph; failed publication or cancellation discards its prepared success report. If a rejected edit's full diagnostic report cannot be saved, a bounded fallback retains rejection status, the primary reason and the report-write error rather than pretending that a complete report exists.

Planner tool results append local mutation notes and relevant warnings to model-visible text. Small results also carry those messages as `details.notes` and `details.warnings`, omitting empty fields. Node deletion reports the count and list of cascade-removed incident edges, and auto-removed redundant direct dependencies are reported with their surviving indirect paths as successful mutation notes. Deletions of non-existent targets remain errors, not successful mutation notes. All blocking diagnostics remain eligible for output, even when the problem predates this edit; overflow changes only their presentation, not validation.

The Planner passes the saved candidate as `previousGraph` to the same compiler invocation. The compiler compares structured advisory facts before and after the edit and returns `mutationWarnings`: only new or changed duplicate-task groups (`W301`) and unrouted feedback markers (`W302`), plus cumulative revision impact (`W304`). W301 identity includes literal task text and group membership; W302 identity is the source node still lacking a feedback route. Unrelated edits and unchanged warning facts do not repeat advice. Resolved warnings reappear if reintroduced, including after extension reload; no session-level seen-warning cache or warning-prose parsing is used. Feedback-disabled projections still omit W302. W304 always describes the current draft relative to the runtime's committed graph, not merely this call's extra impact, and remains visible on subsequent successful edits while that risk exists. Its `since:` output has at most two nonempty groups, with one explanation followed by node ids per group: updated tasks, and original-task reruns using the latest workspace after dependencies complete. Updated-task nodes still follow normal workspace inheritance; they are not all roots using only the source workspace. Grouping shares Runtime's invalidation predicates, does not echo task bodies, and never attributes cumulative impact to the latest unrelated tool call. The tool requires the structured `mutationWarnings` protocol. An older or mismatched compiler without it is rejected with `compiler-response`, rather than falling back to full warnings or simulating incremental advice with a second cache. The compiler and extension must be deployed together.

Conditional feedback rerun-scope descriptions (`W303`) remain omitted from mutation results. The `edit_graph` description explains the continuation semantics; execution details belong to [feedback continuation](runtime.md#feedback-continuation-notices). Full compiler plans retain their existing W301/W302 messages and one W303 per feedback edge in graph order; the CLI's full plan also retains cumulative W304. This Planner-only output projection does not change validation, invalidation, scheduling, tool input schemas or `read_graph` semantics.
